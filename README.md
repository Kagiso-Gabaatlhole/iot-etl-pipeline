# IoT Telemetry ETL Pipeline

A small but engineering-minded **ETL pipeline for synthetic IoT sensor
telemetry**: declarative data validation with per-rule reporting, quarantine of
bad rows, and an **idempotent** load into a SQLite warehouse with a run
manifest. Built as a data-engineering portfolio piece — every number in this
README was produced by actually running the commands shown here on a Windows
machine with Python 3.12.

* **Runtime dependencies:** `pandas` + the Python standard library only
  (config is JSON, warehouse is `sqlite3`, CLI is `argparse`, logging is
  stdlib). `pytest` is the only test dependency.
* **Data provenance: 100 % synthetic**, generated by a seeded script that
  ships in this repo (no network access needed at any point).
* **Status:** a deliberate small-scale project, *not* production-grade — see
  [Limitations](#limitations).

## Data flow

```text
 config/pipeline_config.json        config/validation_rules.json
          |                                   |
          |                                   |
          v                                   v
 +-------------------+              +-------------------+
 | 1. EXTRACT        |              | 2. VALIDATE       |
 | load raw CSVs     |------------->| 15-rule catalogue |
 | as raw strings    |              | error -> reject   |
 | SHA-256 + row     |              | warn  -> flag     |
 | counts            |              +---------+---------+
 +---------+---------+                        |
           |               results/rejects_<run_id>.csv
           |               results/validation_summary_<run_id>.json
           |                                 |
           |                                 v
           |                      +-------------------+
           +--------------------->| 3. TRANSFORM      |
                                  | drop duplicates   |
                                  | quarantine errors |
                                  | coerce types      |
                                  | derive hour,      |
                                  | device_type, date |
                                  +---------+---------+
                                            |
                     data/quarantine/quarantine_<run_id>.csv
                                            |
                                            v
                                  +-------------------+
                                  | 4. LOAD           |
                                  | upsert ON CONFLICT|
                                  | (reading_id)      |
                                  | + load_manifest   |
                                  +---------+---------+
                                            |
                                            v
                                  +-------------------+
                                  | 5. REPORT         |
                                  +---------+---------+
                                            |
                                            v
                            results/quality_report.json
                            results/quality_report.md
```

The warehouse (`data/warehouse.db`) holds two tables:

| Table | Purpose |
| --- | --- |
| `readings` | One row per clean reading, primary key `reading_id` (idempotent upsert target). Deliberately **no** per-run columns. |
| `load_manifest` | Append-only run history: `run_id`, `started_at`, `finished_at`, `rows_in`, `rows_out`, `rejects`, `quarantined_rows`, `warnings`, `flagged_rows`, `duplicates_dropped`, `status`, `source_sha256`. |

## Data provenance (synthetic)

Everything under `data/raw/` is **synthetic data created by
`src/pipeline/generate_data.py`** — no real devices or people are involved.
See [`data/raw/PROVENANCE.md`](data/raw/PROVENANCE.md) for checksums.

* `SEED = 42` — regeneration is deterministic (two runs produced the identical
  SHA-256 `6b11dbdd9d0e1604a7010f33772d243ab6df0e2e5f2580fa0d9a46a98a44110c`).
* **120,000 rows**, **25 devices**, 30-day window
  `2026-09-01T00:00:00 .. 2026-09-30T23:59:59`, columns
  `reading_id, device_id, timestamp, temperature_c, humidity_pct, power_kw`.
* Quality problems are **injected on purpose** so the validate stage has real
  work to do:

| Injected problem | Rows | Severity in the rule catalogue |
| --- | ---: | --- |
| Exact duplicate rows (appended copies) | 1,800 | warn (VR015), dropped by transform |
| Missing values (blank cells) | 400 | error |
| Out-of-range values (negative power, >60 °C, >100 % humidity) | 350 | error |
| Future timestamps (year 2031) | 200 | error |
| Malformed rows (wrong types, `not-a-date`) | 150 | error |
| Unknown device ids (`DEV999`, not in registry) | 100 | error |

## Quickstart

Prerequisites: **Python 3.12** (tested on 3.12.10 / Windows) and pandas
(`pip install -r requirements.txt`). Run everything **from the repository
root** — the CLI resolves relative config paths against the working directory.

```powershell
# 1. The raw CSVs are committed; optionally regenerate them (seeded):
python src/pipeline/generate_data.py          # make build

# 2. Run the full pipeline (extract -> validate -> transform -> load -> report):
python -m etl run --config config/pipeline_config.json   # make run

# 3. Read the data-quality report:
notepad results\quality_report.md             # or open it in any editor
```

## Command line interface

```console
python -m etl run      --config config/pipeline_config.json [--run-id ID] [--log-level INFO]
python -m etl validate --config config/pipeline_config.json [--run-id ID]
python -m etl report   --config config/pipeline_config.json [--run-id ID]
```

* `run` — full pipeline: extract → validate → transform → load → report.
* `validate` — extract + validate only; writes the rejects CSV and the
  validation summary (no warehouse writes).
* `report` — rebuilds `results/quality_report.{json,md}` from stored artifacts
  (validation summary + manifest). Without `--run-id` it targets the most
  recently loaded run.
* `--run-id` defaults to a generated id like `run_20261029T002308_a1b2`; the
  id is used in artifact file names and the per-run log
  (`logs/etl_<run_id>.log`).

### Exit codes

| Code | Meaning | Triggered by |
| ---: | --- | --- |
| `0` | Success | `run` completed (error rows quarantined); `validate` found no error-severity violations; `report` written |
| `1` | **Validation failed at error severity** | `validate` when any `error` rule fired; `run` when `validation.abort_on_error=true` and error rows exist (report is still written) |
| `2` | Unexpected / configuration error | Missing or invalid JSON config, missing rules file or input CSV, unknown run artifacts for `report`, invalid `--run-id`, unhandled exceptions (argparse usage errors also exit 2) |

Observed on the committed data:

```console
> python -m etl validate --config config/pipeline_config.json --run-id validate_demo
... | ERROR   | etl.orchestrator | run.finish command=validate run_id=validate_demo status=validation_failed exit_code=1 rules=15
--- validate exit 1 ---        # 1,200 rows carry error-severity violations

> python -m etl report --config config/pipeline_config.json
... | INFO    | etl.orchestrator | run.finish command=report run_id=run_002 status=completed exit_code=0
--- report exit 0 ---
```

### Logging

Structured, human-readable logging through the stdlib (`key=value` payloads):

* **console** — compact `HH:MM:SS | LEVEL | stage | message`;
* **per-run file** — `logs/etl_<run_id>.log` with full timestamps and
  `[run_id=...]` on every line (see `logs/etl_run_002.log` after a run;
  log files are git-ignored).

## Rule catalogue

Validation is driven by `config/validation_rules.json` — data, not code. Each
rule declares `id`, `description`, `field`, `severity` (`error` → row
quarantined, `warn` → row loaded with a `warning_flags` entry) and a
`predicate`. The "Violations" column below is what the committed data actually
produced (from `results/quality_report.md`; deterministic for seed 42):

| Rule | Severity | Field | Predicate | Violations | Description |
| --- | --- | --- | --- | ---: | --- |
| VR001 | error | `reading_id` | `not_null` | 28 | reading_id must not be empty |
| VR002 | error | `device_id` | `not_null` | 0 | device_id must not be empty |
| VR003 | error | `timestamp` | `not_null` | 118 | timestamp must not be empty |
| VR004 | error | `timestamp` | `iso_datetime` | 144 | timestamp must be a valid ISO-8601 datetime (`YYYY-MM-DDTHH:MM:SS`) |
| VR005 | error | `timestamp` | `not_future` | 344 | timestamp must not be in the future |
| VR006 | error | `device_id` | `in_set` | 100 | device_id must exist in the device registry |
| VR007 | error | `temperature_c` | `numeric` | 34 | temperature_c must be numeric |
| VR008 | error | `temperature_c` | `range -40..60` | 149 | temperature_c must be within −40..60 °C |
| VR009 | error | `humidity_pct` | `numeric` | 196 | humidity_pct must be numeric |
| VR010 | error | `humidity_pct` | `range 0..100` | 330 | humidity_pct must be within 0..100 percent |
| VR011 | error | `power_kw` | `numeric` | 148 | power_kw must be numeric |
| VR012 | error | `power_kw` | `range 0..15` | 249 | power_kw must be within 0..15 kW (negative power is impossible) |
| VR013 | warn | `temperature_c` | `range max 45` | 2,848 | temperature_c above 45 °C (or not evaluable as a number) |
| VR014 | warn | `humidity_pct` | `range max 95` | 3,838 | humidity_pct above 95 percent (or not evaluable as a number) |
| VR015 | warn | all columns | `unique` | 1,800 | exact duplicate reading row |

Totals on the committed data: **1,840 error-level violations across 1,200
rows** (quarantined) and **8,486 warn-level violations across 8,318 rows**
(flagged; some rows trip more than one rule).

Predicate semantics (all vectorised over the frame, `True` = row passes):

| Predicate | Passes when |
| --- | --- |
| `not_null` | value is present and not blank |
| `numeric` | value coerces to a number |
| `range` | numeric value is inside inclusive `min`/`max` bounds |
| `iso_datetime` | value matches `YYYY-MM-DDTHH:MM:SS` **and** parses |
| `not_future` | parseable value is not after the current wall clock |
| `in_set` | value is in a literal list or a named context set (device registry) |
| `unique` | no earlier row in the frame is byte-for-byte identical |

Predicates **fail closed**: an unparseable value never satisfies `numeric`,
`range`, `iso_datetime` or `not_future`, so malformed rows cannot slip past a
range rule. A row can carry several rule ids at once (e.g. a blank timestamp
trips VR003 + VR004 + VR005) — that is why violation totals exceed row counts.

## Configuration

### `config/pipeline_config.json`

```jsonc
{
  "pipeline_name": "iot-telemetry-etl",
  "version": "1.0.0",
  "paths": {
    "readings_csv": "data/raw/iot_readings.csv",      // input CSVs
    "device_registry_csv": "data/raw/device_registry.csv",
    "validation_rules": "config/validation_rules.json", // rule catalogue
    "warehouse_db": "data/warehouse.db",                // SQLite target
    "results_dir": "results",                           // reports, rejects, summaries
    "logs_dir": "logs",                                 // per-run logs
    "quarantine_dir": "data/quarantine"                 // error-level rows
  },
  "validation": { "abort_on_error": false },  // true => `run` exits 1 on error rows
  "logging": { "level": "INFO" }              // DEBUG | INFO | WARNING | ERROR
}
```

* Relative paths resolve against the **current working directory** (run from
  the repository root); absolute paths work too (the tests use them).
* Unknown/missing keys fail fast with exit code 2 (`etl.config.ConfigError`).
* JSON was chosen over YAML on purpose: one less dependency, stdlib parsing.
  UTF-8 with or without a BOM is accepted (Windows editors add a BOM).

### `config/validation_rules.json`

```jsonc
{
  "schema_version": 1,
  "rules": [
    {
      "id": "VR012",
      "description": "power_kw must be within 0..15 kW (negative power is impossible)",
      "field": "power_kw",
      "severity": "error",                       // error => quarantine, warn => flag
      "predicate": { "type": "range", "min": 0, "max": 15 }
    }
  ]
}
```

The loader validates the catalogue itself (unique ids, known severities,
supported predicates, required fields) and exits 2 on a malformed file —
adding a rule is a config change, never a code change.

## Tests

```console
> python -m pytest tests -q
80 passed in 3.92s
```

80 tests cover:

| Area | What is proven |
| --- | --- |
| Rule engine | Each of the 15 rules catches exactly its intended bad row in a fixture (16 parametrised cases), duplicate handling, pass/fail status, catalogue-loading failures |
| Extract | SHA-256 matches `hashlib`, row counts, raw strings preserved, missing files/columns raise |
| Transform | Exact duplicates dropped (first kept), error rows quarantined, `hour`/`date`/`device_type` derivation, float coercion, `warning_flags` joining, end-to-end counts on the 420-row fixture |
| Load | **Idempotence: load twice → equal row count *and* equal content digest**, manifest rows, upsert of changed values, one manifest row per `run_id` |
| Report | All required fields present, not-executed sections for aborted runs, Markdown rendering, end-to-end report counts |
| Config | Missing file / invalid JSON / missing keys / bad types → `ConfigError` |
| CLI | `run` → 0 with all artifacts, `validate` → 1 on error rows, `validate` → 0 on clean data, `abort_on_error` → 1, bad config → 2, unknown run → 2, `python -m etl` subprocess smoke tests |

Tests never touch the committed CSVs: each test generates a small 420-row
dataset into `tmp_path` with a different seed.

## Design decisions

**Declarative rule catalogue (JSON).** Data-quality policy lives in
`config/validation_rules.json`, not in `if` statements. Rules are reviewable
in a PR without reading Python, counts are reported per rule id, and the same
catalogue drives rejects, flags and the report. The engine stays tiny: seven
generic predicates instead of one function per rule. The catalogue file itself
is validated (ids, severities, predicates) so a config typo fails fast with
exit code 2 rather than silently skipping checks.

**Load manifest.** Every load appends a row to `load_manifest` with the run
id, timestamps, rows in/out, rejects, warnings and the source file's SHA-256.
That gives an audit trail ("what ran, when, on which bytes, with what
outcome") and makes the report reconstructible after the fact — `etl report`
rebuilds `quality_report.{json,md}` purely from the stored summary + manifest
without re-reading the raw data.

**Idempotence approach.** `readings` is keyed by the natural key
`reading_id` and loaded with `INSERT ... ON CONFLICT(reading_id) DO UPDATE`.
Loading the same cleaned data twice therefore leaves the table content
byte-identical (proved by the content digest above). Per-run metadata is
deliberately **not** stored on `readings` (no `run_id`/`loaded_at` columns) —
otherwise a second run would rewrite every row and idempotence would be
impossible to demonstrate. Provenance lives in the manifest instead.

**Quarantine by default, abort on demand.** Error-level rows are moved out of
the load path (`data/quarantine/`) and the run still completes — one bad
sensor should not block 117k good rows. For strict situations,
`validation.abort_on_error: true` stops `run` after validation (exit 1, report
still written), and `etl validate` is the always-strict gate.

**Fail-closed predicates.** An unparseable value never passes `numeric`,
`range`, `iso_datetime` or `not_future`. Malformed data can therefore never be
"valid by accident", even if someone edits a range rule later.

**String-typed extract.** The raw CSVs are read as strings (`dtype=str`,
`na_filter=False`). pandas type inference is exactly what a malformed row
should not survive; coercion happens *after* validation, in transform.

**JSON over YAML, stdlib over frameworks.** Config, logging, CLI, checksums
and SQLite are all standard library. The only runtime dependency is pandas —
chosen because vectorised rule evaluation over 120k rows × 15 rules stays in
the low seconds and the dedupe/derive logic stays readable.

**Zero-install CLI.** The repo root contains a tiny `etl/` shim that
redirects `etl.__path__` to `src/etl/`, so `python -m etl ...` works from a
fresh clone with no `pip install -e .` step (which would need build
dependencies/network in restricted environments). Tests bypass the shim:
`conftest.py` puts `src/` first on `sys.path`, so the suite imports the real
package directly.

**Honest exit codes.** 0 = success, 1 = validation failed where that is fatal
for the command, 2 = configuration or unexpected errors. The distinction
between "quarantined and completed" (0) and "gate failed" (1) is deliberate
and documented rather than guessed by the caller.

## Limitations

This is a **small but engineering-minded** portfolio project, not a production
system. Known limitations:

* **Single machine, single process.** No distributed processing — everything
  runs in one Python process on one machine (120k rows in ~2 seconds, which is
  exactly why there is no Spark here, but it also means no horizontal scale).
* **No orchestration.** No Airflow/Dagster/Prefect: no scheduling, retries,
  backfills, dependencies or SLAs. Runs are manual CLI invocations.
* **Synthetic data.** The dataset is generated by a seeded script and its
  quality problems are injected, not observed. Real IoT feeds have different
  messiness (clock skew, bursts, sensor drift, mixed encodings). All counts in
  this README are properties of *this* generator at seed 42.
* **SQLite is a teaching warehouse.** Single-writer, file-based, no
  concurrency control across processes, no partitioning or retention policy.
  Fine for a portfolio demo, wrong for many concurrent writers.
* **Batch CSV only.** One flat input file; no streaming, no late-arriving
  data, no schema evolution (a renamed column is an error, not a migration).
* **Whole-row quarantine.** Bad rows are rejected wholesale — there is no
  repair/imputation step and no per-rule tolerance thresholds.
* **Load is insert/update only.** The upsert never deletes: if a reading
  disappears upstream it stays in the warehouse.
* **Wall-clock dependence.** The `not_future` rule uses the local system
  clock and naive timestamps; timezone handling is not implemented.
* **No observability beyond logs.** No metrics pipeline or alerting — the
  per-run log file and report are the monitoring story.
* **No PII/security story.** The data is synthetic, so access control,
  encryption and audit requirements are out of scope.

## Possible extensions

| Extension | What it would add |
| --- | --- |
| **Airflow** (or Dagster/Prefect) | Scheduled DAG of the five stages, retries, SLAs, backfills; each stage is already a pure, testable task |
| **PostgreSQL** | Swap the `sqlite3` calls for `psycopg` (the upsert SQL is standard `ON CONFLICT`), real concurrency, constraints, managed backups |
| **Great Expectations** | Suites + data docs alongside the built-in catalogue; the rule catalogue maps 1:1 onto expectations, and the report already plays the role of data docs |
| **dbt** | SQL-based modelling and tests on top of the warehouse, turning `readings` into analytics-ready marts |
| Streaming (Kafka) | Windowed rules over a live feed instead of batch CSV |
| Monitoring | Export per-rule counts as metrics; alert when the reject rate crosses a threshold |
